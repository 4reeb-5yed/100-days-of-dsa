Building an Autonomous CI/CD Pipeline Across Multiple GitHub Repos

This guide teaches you how to build a fully automated delivery system using GitHub Actions. You'll create a scheduled pipeline that clones content from one private repository, tests it in another, and delivers it to a third via a real pull request — with CI-gated merges and zero manual intervention after initial setup.

This is a CI/CD and GitHub Actions learning project focused on automation architecture, secure credential handling, and fail-closed pipeline design.

Architecture Overview

The pipeline spans three separate GitHub repositories, each with a distinct role:

Why Three Repositories?

This separation isn't arbitrary — each repo has a specific security and organizational role:

  • Private data repo — Contains your content bank. It only needs to be readable by the orchestrator. Nobody needs to write to it after creation.
  • Private orchestrator repo — Holds your automation logic and state. It needs write access to both itself (to update progress/state.json) and to the output repo (to create branches and PRs).
  • Public output repo — Your visible project. It has no secrets. CI runs independently on it, and only accepts changes via PR after tests pass.

This follows the principle of least privilege: if the orchestrator is compromised, it can only write to the output repo — not to the data repo or any other project.

Prerequisites

What You Need Before Starting

  • A GitHub account — Free accounts work fine for this project.
  • Basic GitHub familiarity — You should know how to create a repository, navigate settings, and view files. If you've never pushed code to GitHub before, consider doing a basic tutorial first.
  • No git CLI required — This guide explains everything using GitHub's web interface where possible, plus the gh CLI (which GitHub Actions runners have pre-installed, so we'll use it in automation scripts).

What is a Fine-grained PAT?

A Personal Access Token (PAT) is like a password that lets scripts act as you on GitHub. A fine-grained PAT is a newer, more secure type that lets you grant access to specific repositories with specific permissions — rather than your entire account.

⚠️ Why This Project Needs a Fine-grained PAT

GitHub Actions runners get a special GITHUB_TOKEN automatically, but that token can only access the repo where the workflow runs. Since our automation needs to write to two repos (the output repo and its own state), we need our own token with cross-repo permissions. A fine-grained PAT gives us exactly that control.

The gh CLI

The gh command-line tool is GitHub's official CLI. GitHub Actions runners come with it pre-installed, so we can use it in our automation scripts to:

  • Create branches
  • Open pull requests
  • Check CI status
  • Merge pull requests

You don't need to install gh locally unless you want to test the scripts on your own machine.

Step-by-Step Build

1

Create Three Empty GitHub Repositories

We need three repositories. Each should be initialized with a README so a main branch exists immediately.

⚠️ Why Initialize with a README?

An empty GitHub repository has no branches at all — not even main. You can't create branches or open PRs against a repo with no default branch. Initializing with a README creates the main branch automatically, letting you immediately start working.

Create these three repositories in your GitHub account:

  1. dsa-data (private) — Your question bank
  2. dsa-orchestrator (private) — Your automation logic
  3. dsa-output (public) — Your visible project

For each one: click New repository, enter the name, choose Private or Public as appropriate, check Add a README file, and click Create repository.

💡 Tip

Keep the repo names simple and all-lowercase with hyphens. Python module names use underscores, but repo names can use hyphens. We'll handle the distinction in the scripts.

How to Write Good Problem Bank Entries

  • Paraphrase problems — Don't copy problem text verbatim from LeetCode or other sites. Rewrite the problem description in your own words.
  • Spread difficulty — Include a mix of easy, medium, and hard problems.
  • Cover multiple topics — Arrays, strings, linked lists, trees, dynamic programming, etc.
  • One solution per entry — Keep it simple. Multiple solutions can come later.
💡 Tip

The day number in each entry is the order in the bank, not today's date. The orchestrator tracks which problems have been used in its own state file.

This is the heart of the pipeline. It contains:

  • A Python script that does the actual work
  • A state file to track progress
  • A GitHub Actions workflow to run it on a schedule

File 2: pick_and_commit.py

This script runs inside the GitHub Actions runner:

dsa-orchestrator / pick_and_commit.py
#!/usr/bin/env python3
"""
Orchestrator script: picks a problem from the data repo,
writes files to the output repo, opens a PR, waits for CI,
and merges only if CI passes.
"""

import json
import os
import subprocess
import time
import sys

# Configuration
DATA_REPO = "YOUR_USERNAME/dsa-data"
OUTPUT_REPO = "YOUR_USERNAME/dsa-output"
ORCHESTRATOR_REPO = "YOUR_USERNAME/dsa-orchestrator"
GITHUB_TOKEN = os.environ["GH_PAT"]
TODAY = "2026-07-04"  # In real use, calculate from datetime

# Paths
SCRIPT_DIR = os.path.dirname(os.path.abspath(__file__))
STATE_FILE = os.path.join(SCRIPT_DIR, "progress", "state.json")
DATA_BRANCH = "main"


def run(cmd, check=True, capture_output=True):
    """Run a shell command."""
    print(f"Running: {cmd}")
    result = subprocess.run(
        cmd, shell=True, check=check, capture_output=capture_output, text=True
    )
    if result.stdout:
        print(result.stdout.strip())
    return result


def load_state():
    """Load current progress state."""
    with open(STATE_FILE) as f:
        return json.load(f)


def save_state(state):
    """Save progress state."""
    with open(STATE_FILE, "w") as f:
        json.dump(state, f, indent=2)


def git_config():
    """Configure git with attribution."""
    run("git config --global user.email 'YOUR_NOREPLY_EMAIL@users.noreply.github.com'")
    run("git config --global user.name 'Your Name'")


def clone_repos():
    """Clone both repos using the fine-grained PAT."""
    base_url = f"https://{GITHUB_TOKEN}@github.com/"
    
    # Clone data repo
    run(f"git clone {base_url}{DATA_REPO} data-repo-temp")
    
    # Clone output repo
    run(f"git clone {base_url}{OUTPUT_REPO} output-repo-temp")


def pick_problem(state):
    """Pick the next problem from the bank."""
    # Load the bank
    with open("data-repo-temp/problem-bank.json") as f:
        bank = json.load(f)
    
    # Find next unpicked problem
    next_day = state["last_day"] + 1
    
    for entry in bank:
        if entry["day"] == next_day:
            return entry
    
    return None  # Bank exhausted


def write_files(problem):
    """Write solution and test files to the output repo."""
    os.chdir("output-repo-temp")
    
    # Create directories
    os.makedirs("solutions", exist_ok=True)
    os.makedirs("tests", exist_ok=True)
    
    # Write solution file
    solution_path = f"solutions/{problem['solution_file']}"
    with open(solution_path, "w") as f:
        f.write(problem["solution_code"])
    print(f"Written: {solution_path}")
    
    # Write test file
    test_path = f"tests/{problem['test_file']}"
    with open(test_path, "w") as f:
        f.write(problem["test_code"])
    print(f"Written: {test_path}")
    
    # Update README with progress
    update_readme(problem)
    
    os.chdir("..")


def update_readme(problem):
    """Update the README.md progress table."""
    readme_path = "README.md"
    
    # Simple update: append to progress table
    new_row = f"| {problem['day']:03d} | {problem['title']} | {problem['topic']} | {problem['difficulty']} | {TODAY} |"
    
    if os.path.exists(readme_path):
        with open(readme_path) as f:
            content = f.read()
        
        # Insert before PROGRESS_TABLE_END
        content = content.replace(
            "",
            f"{new_row}\n"
        )
        
        with open(readme_path, "w") as f:
            f.write(content)


def run_local_tests():
    """Run pytest locally before pushing anything."""
    print("Running local tests...")
    result = run("pip install pytest -q && pytest -q", check=False)
    
    if result.returncode != 0:
        print("TESTS FAILED locally — aborting pipeline!")
        sys.exit(1)
    
    print("Local tests passed!")


def create_pr_and_merge(state, problem):
    """Create branch, commit, push, open PR, wait for CI, merge."""
    os.chdir("output-repo-temp")
    git_config()
    
    # Create a new branch for today
    branch_name = f"daily/day-{problem['day']:03d}"
    run(f"git checkout -b {branch_name}")
    run("git add solutions/ tests/ README.md")
    run(f"git commit -m 'Day {problem['day']}: {problem['title']}'")
    run(f"git push -u origin {branch_name}")
    
    # Open PR using gh CLI
    pr_url = run(
        f'gh pr create --title "Day {problem["day"]}: {problem["title"]}" '
        f'--body "Automated daily delivery" --repo {OUTPUT_REPO}',
        capture_output=True
    ).stdout.strip()
    
    print(f"PR opened: {pr_url}")
    
    # Poll for CI status
    print("Waiting for CI to pass...")
    max_wait = 600  # 10 minutes
    interval = 15
    elapsed = 0
    
    while elapsed < max_wait:
        time.sleep(interval)
        elapsed += interval
        
        # Check CI status
        result = run(
            f'gh pr status --repo {OUTPUT_REPO} --json statusCheckRollup',
            check=False, capture_output=True
        )
        
        # Parse the JSON output to check status
        # For simplicity, we'll use a helper script or gh api
        check_result = subprocess.run(
            f'gh api repos/YOUR_USERNAME/dsa-output/commits/main/status',
            shell=True, capture_output=True, text=True
        )
        
        if check_result.returncode == 0:
            status_data = json.loads(check_result.stdout)
            state_val = status_data.get("state", "")
            
            if state_val == "success":
                print("CI passed!")
                break
            elif state_val == "failure":
                print("CI failed — aborting merge!")
                sys.exit(1)
    
    # Merge the PR
    print("Merging PR...")
    run(f'gh pr merge --squash --repo {OUTPUT_REPO}')
    
    # Update state
    state["last_run"] = TODAY
    state["last_day"] = problem["day"]
    state["total_delivered"] += 1
    
    os.chdir("..")


def update_orchestrator_state(state):
    """Update the orchestrator's own state file."""
    os.chdir("orchestrator-repo-temp")
    git_config()
    
    run("git checkout main")
    
    # Update state file
    with open(STATE_FILE) as f:
        current = json.load(f)
    current.update(state)
    
    with open(STATE_FILE, "w") as f:
        json.dump(current, f, indent=2)
    
    run("git add progress/state.json")
    run(f'git commit -m "Update state: day {state["last_day"]}"')
    run("git push")
    
    os.chdir("..")


def main():
    print("=" * 50)
    print("Starting daily DSA delivery pipeline")
    print("=" * 50)
    
    # Load state
    state = load_state()
    
    # Guard: already ran today?
    if state["last_run"] == TODAY:
        print(f"Already ran today ({TODAY}). Skipping.")
        return
    
    # Clone repos
    print("Cloning repositories...")
    clone_repos()
    
    # Pick next problem
    problem = pick_problem(state)
    
    if problem is None:
        print("No more problems in bank! Pipeline complete.")
        return
    
    # Write files to output repo
    print(f"Picking problem: Day {problem['day']} - {problem['title']}")
    write_files(problem)
    
    # Run local tests
    run_local_tests()
    
    # Create PR and wait for CI
    create_pr_and_merge(state, problem)
    
    # Update orchestrator state
    update_orchestrator_state(state)
    
    print("Pipeline complete!")


if __name__ == "__main__":
    main()

File 3: daily-dsa.yml

The GitHub Actions workflow that runs the script:

dsa-orchestrator / .github / workflows / daily-dsa.yml
name: Daily DSA Delivery

on:
  # Run every day at 9 AM UTC
  schedule:
    - cron: '0 9 * * *'
  
  # Allow manual trigger for testing
  workflow_dispatch:

jobs:
  deliver:
    runs-on: ubuntu-latest
    
    steps:
      - name: Checkout orchestrator repo
        uses: actions/checkout@v4
        with:
          token: ${{ secrets.GH_PAT }}
          path: orchestrator-repo-temp
      
      - name: Run orchestrator script
        env:
          GH_PAT: ${{ secrets.GH_PAT }}
        run: |
          python3 pick_and_commit.py

name: CI

  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest -q
🐛 Why pull_request and NOT pull_request_target?

pull_request_target gives your workflow access to secrets when processing PRs from forks. This is a security risk: a malicious PR could steal those secrets. We use pull_request instead, which doesn't expose secrets to fork PRs. Since our output repo is the main project (not a fork scenario), this is safe and correct.

File 2: pytest.ini

dsa-output / pytest.ini
[pytest]
pythonpath = .
⚠️ Why pythonpath = . Is Required

When you run pytest tests/, pytest changes into the tests/ directory. It then looks for imports like from solutions.day_001_two_sum import two_sum relative to tests/ — but solutions/ is at the project root, not inside tests/.

Setting pythonpath = . adds the project root to Python's search path (sys.path), so the import can find solutions/ regardless of which directory pytest runs from.

Generate the Fine-grained PAT

This token is what lets the orchestrator write to both repos. Follow these exact steps:

  1. Go to GitHub Settings (click your profile picture → Settings)
  2. In the left sidebar, scroll to the bottom and click Developer settings
  3. Click Personal access tokens → Fine-grained tokens
  4. Click Generate new token

Token settings:

  • Token name: dsa-orchestrator
  • Expiration: 30 days (or 90 days — your choice)
  • Description: Access for daily DSA orchestrator

Repository access:

  • Select Only select repositories
  • Choose: dsa-data, dsa-orchestrator, dsa-output

Permissions for each repo:

  • dsa-data (contents): Read-only — the script only clones and reads this repo
  • dsa-orchestrator (contents): Read and write — needs to push state updates
  • dsa-output (contents): Read and write — needs to create branches, commits, and PRs
  • dsa-output (pull requests): Read and write — needs to create and merge PRs
⚠️ Important

Do NOT grant admin permissions. The orchestrator doesn't need to bypass branch protections — that's intentional. CI-gated merges are the point.

After clicking Generate token, copy the token immediately — GitHub only shows it once!

Add the Token as a Secret

In the dsa-orchestrator repo:

  1. Go to Settings → Secrets and variables → Actions
  2. Click New repository secret
  3. Name: GH_PAT
  4. Value: paste your token
  5. Click Add secret

Configure Repository Settings

Orchestrator Repo: Workflow Permissions

The orchestrator repo needs permission to push commits and create PRs via the workflow:

  1. Go to Settings → Actions → General
  2. Under Workflow permissions, select Read and write permissions
  3. Click Save

Output Repo: Branch Protection

This is critical for the fail-closed design. Go to dsa-output → Settings → Branches → Add branch protection rule:

  • Branch name pattern: main
  • ✅ Require a pull request before merging
    Ensures changes go through PR review, not direct push
  • ✅ Require status checks to pass before merging
    Only enable this AFTER your CI workflow runs successfully at least once
  • 🔲 Require approvals — leave unchecked
    We want automated merges without human approval
  • 🔲 Do not allow bypassing the above settings — leave as default
    This is the important one: administrators cannot bypass either
🐛 Common Mistake

If you check "Allow administrators to bypass" or if your account is an admin and you've enabled bypass, the automated merge will succeed even when CI fails. The orchestrator's gh pr merge command has an --admin flag that does exactly this — and that's why we don't use it.

Fix Commit Attribution

GitHub counts contributions (like commits on your profile) only when the commit's author email matches an email verified on your GitHub account.

💡 Why This Matters

When the script runs as "GitHub Actions," the default commit attribution goes to github-action[bot] — not your personal account. Setting user.email to your GitHub noreply address ensures commits count toward your contribution graph.

Get Your GitHub Noreply Address

  1. Go to Settings → Emails
  2. Check that Keep my email addresses private is enabled
  3. Look for the generated noreply address — it looks like:
    12345678+YOURUSERNAME@users.noreply.github.com
  4. Copy this address

Set the Email in the Script

In pick_and_commit.py, update the git_config() function:

def git_config():
    """Configure git with attribution."""
    run("git config --global user.email '12345678+YOURUSERNAME@users.noreply.github.com'")
    run("git config --global user.name 'Your Name'")

Replace 12345678+YOURUSERNAME@users.noreply.github.com with your actual noreply address from the settings page.

Troubleshooting

Real bugs that have occurred in this pipeline, with causes and fixes:

Bug 1: Hyphens in Slug Break Python Imports

Symptom

SyntaxError: invalid syntax or ModuleNotFoundError when Python tries to import a file with hyphens in the name.

Cause

Python module names must follow identifier rules: letters, numbers, and underscores only. from solutions.day-001-two-sum import ... is invalid Python syntax because day-001-two-sum contains hyphens.

Fix

Use underscores in Python files: day_001_two_sum.py. Human-facing names (branch names, PR titles) can keep hyphens — they're only Python that cares.

Bug 2: Merge --admin Flag Silently Bypasses CI

Symptom

A PR merged even though CI was failing. You only noticed because you checked manually later.

Cause

The gh pr merge --admin flag tells GitHub "merge this even if I'm an admin and bypass protections." When your account is an admin on the repo, this flag lets CI failures be ignored.

Fix

Don't use --admin. Use gh pr merge without flags. This respects branch protection. Also, ensure branch protection is configured to not allow admin bypass.

🐛 General Lesson

Override flags exist for genuine emergencies, but they defeat the safety mechanism they're meant to be an exception to. Treat them as a last resort, not a normal tool.

Bug 3: ModuleNotFoundError in CI but Tests Pass Locally

Symptom

pytest runs fine on your machine, but the CI workflow shows ModuleNotFoundError: No module named 'solutions'.

Cause

When pytest runs from the project root (pytest tests/), Python can find the solutions/ directory. But when CI runs pytest after actions/checkout, the working directory might differ, or pytest might change directories internally.

Fix

Add pytest.ini with pythonpath = . at the repo root. This ensures the project root is always in Python's search path regardless of which directory pytest runs from.

Bug 4: Commits Not Appearing on Contribution Graph

Symptom

The pipeline runs successfully, PRs merge, but the commits don't show up on your GitHub contribution graph.

Cause

GitHub only counts contributions from verified email addresses. If the commit author email is not verified on your account (or is the default github-action[bot] email), it won't appear in your graph.

Fix

Set git config user.email to your GitHub-issued noreply address (Settings → Emails → Keep my email addresses private → copy the generated address). This is a neutral technical requirement — commit attribution is handled this way by design.

Why This Architecture

FAQ: The Reasoning Behind Each Choice

Why split credentials into build-time vs runtime scopes?

The fine-grained PAT has read-only access to the data repo but read-write access to the output repo. If the orchestrator is ever compromised, it can only write to the output repo — not to the data repo (where the content lives) or any other repository.

Why test locally AND independently in CI (two gates)?

Local tests catch obvious failures before wasting CI resources. Independent CI tests prove the code works in a clean environment, not just "it worked on my machine." Two gates mean a single test failure can't accidentally skip verification.

Why pull_request over pull_request_target?

pull_request_target exposes secrets to workflows running on fork PRs. A malicious PR author could steal those secrets. Since our output repo is the main project (not a fork scenario), pull_request is both safer and sufficient.

Why no admin bypass on merges?

If administrators can bypass CI, then the pipeline can too (with --admin flags). By removing admin bypass from branch protection, we ensure the automation can't circumvent its own safety net — not even "just this once."
